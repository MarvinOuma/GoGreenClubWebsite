# Release and migration notes

## Firebase configuration

- Confirm the staging and production project IDs, Hosting site and custom domain, web App ID, default Firestore database, Storage bucket, and Auth authorized domains. The current repository default is `gogreen-club-c5b8d`. Use an explicit `--project` for each Firebase command.
- Use an approved deploy identity. The Functions runtime is Node.js 22 in `us-central1`. Enable billing and the services required for Functions and scheduled Pub/Sub. Confirm Email/Password and Google providers in Firebase Auth and verify an existing administrator can sign in with the `admin: true` claim.
- Create `PARTNER_RATE_KEY` in Secret Manager as a private, randomly generated value for each project. The first-generation `submitPartnerInquiry` callable binds that secret. Use `firebase functions:secrets:set PARTNER_RATE_KEY --project "$STAGING_PROJECT"` and enter it at the prompt. Keep it out of dotenv files, Git, command arguments and the web build. Register the web app with Firebase App Check and add its reCAPTCHA v3 **site** key to `VITE_FIREBASE_APP_CHECK_SITE_KEY`. The callable requires a verified App Check token by default. An explicit `PARTNER_ENFORCE_APP_CHECK=false` in the staging Functions runtime allows a short diagnostic window if needed. Remove it or set it to `true` and redeploy before staging sign-off. Confirm that distinct clients receive independent limits behind the deployed ingress. The hourly limits are five inquiries per client IP, three per email address, and 100 globally. The configured Firestore TTL removes expired HMAC-derived limiter records. [Firebase Functions environment and secrets](https://firebase.google.com/docs/functions/1st-gen/config-env-1st)
- Storage rules require the Firebase Storage service agent to read Firestore for administrator revocation and active status. Enable the permission when Firebase prompts. Content images are public-by-URL assets. Use only approved images for event, partner, and blog media, including media uploaded while editing drafts. Inventory existing profile-photo download tokens if any were distributed. [Firebase cross-service permissions](https://firebase.google.com/docs/rules/manage-deploy#manage_permissions_for_cross-service_cloud_storage_security_rules)
- Deploy the indexes in `firestore.indexes.json` and wait for them to become ready. Check the aggregation query for `pointAwards` in staging. Verify production index readiness in the Firebase console. [Firestore aggregation queries](https://firebase.google.com/docs/firestore/query-data/aggregation-queries)

## Legacy data review

1. Export and back up the approved target before cutover. Review Firestore and Storage using least-privileged access. Review the removed Auth export in earlier Git commits with the privacy owner and repository collaborators. Any history cleanup requires separate approval and coordination.
2. Review historical registrations by event and user before accepting legacy attendance corrections. The first successful registration or cancellation for an older event initializes its count from distinct participant IDs. Old IDs continue to work. Unreviewed duplicates can be cleared when the member cancels or an administrator removes the participant. Where a duplicate includes attendance or a legacy award has an ambiguous balance, review the records and points before a controlled repair.
3. Public waste and planting totals start with reports that have a server-written ledger entry. An administrator can verify a previously approved report in the Approval Queue after checking the original evidence. This adds its quantities to the next publication and preserves past Green Points. Review historically awarded points separately where earlier records disagree.
4. Review existing event dates and any manually completed or cancelled states. Date-only events and registration deadlines run through the end of the calendar day in Africa/Nairobi. Timestamped events retain their instant. The admin date editor displays dates in Nairobi time.
5. Confirm retention before enabling destructive production operations. Event deletion hides the event, removes registrations in batches, and retains awarded points and their ledger. Account deletion disables the account, removes registrations, pending and rejected reports, and profile media, and removes the reporter and narrative from retained approved reports. A restricted audit record and an inactive tombstone remain. Retry the same action if cleanup is interrupted. Legacy content images without tracked object keys and any interrupted uploads need a separate read-only inventory and approved cleanup.
6. Ask club leadership to confirm authorized donation details and any official social channels or photos for publication. The public Support section currently routes inquiries to the club contact form.

## Staging deployment checklist

### Project owner setup

- [ ] Confirm the canonical production URL and Firebase project. The public checks in [the pre-release review](PRE_RELEASE_REVIEW.md) found two separate live projects. Create or identify a third, isolated Firebase project for staging. A preview channel inside either production project shares its backend.
- [ ] Enable Blaze billing and create the default Firestore database, Storage bucket and Hosting site in staging. Enable Email/Password and Google Auth and authorize the staging domain. Create disposable staging member and admin accounts. Bootstrap an admin custom claim through an authorized Admin SDK process. Confirm the operator has permission to deploy and the runtime has access to Auth, Firestore, Storage and the inquiry secret. Enable the Storage Rules Firestore service-agent role when prompted. [Firebase Functions runtime setup](https://firebase.google.com/docs/functions/manage-functions)
- [ ] Register the staging web app and domain for App Check with reCAPTCHA v3. Put the reCAPTCHA secret in the Firebase App Check console and its public site key in the staging build environment. Create the separate `PARTNER_RATE_KEY` Secret Manager value. [Firebase App Check setup](https://firebase.google.com/docs/app-check/web/recaptcha-provider)
- [ ] Supply the matching staging `VITE_FIREBASE_*` web settings from Project settings and set `VITE_FIREBASE_EMULATORS=false`. Use approved test fixtures and authorized photos. Never copy production user identities or partner inquiries into staging.

### After explicit staging deployment approval

1. Confirm `STAGING_PROJECT` is the actual isolated project ID. Run `npm ci`, `npm ci --prefix functions`, `npm run lint`, `npm test`, `npm run test:emulator` and `npm run test:browser`. Build with the staging environment and confirm the resulting web bundle targets staging.
2. Deploy indexes and TTL with `firebase deploy --only firestore:indexes --project "$STAGING_PROJECT"`. Review the proposed changes and wait for the indexes to become ready.
3. Deploy Functions with `firebase deploy --only functions --project "$STAGING_PROJECT"`. Verify Node.js 22, region `us-central1`, default bucket, Secret Manager access and scheduled trigger configuration.
4. Deploy Firestore and Storage rules with `firebase deploy --only firestore:rules,storage --project "$STAGING_PROJECT"`. Confirm the Storage Rules service agent permission, then deploy the staged build with `firebase deploy --only hosting --project "$STAGING_PROJECT"`. Keep staging URLs and web configuration separate from the production cutover.
5. Run the staging checks below. Record the commit, Hosting release, ruleset versions, Functions versions, configuration and index status. Production requires its own approval, backups, migration rehearsal and a coordinated cutover. Keep hardened rules in place if the UI needs rollback. The old client uses a different write contract, so use a compatible frontend revision or a maintenance page.

### Staging checks that require deployed Firebase

- [ ] Confirm Google sign-in, email signup and password reset delivery, role refresh and inactive-account behavior. Check public/member/admin boundaries against deployed rules with authorized disposable accounts.
- [ ] Test registration at capacity, cancellation, report review, attendance reversal and ledger consistency. Verify legacy fixtures including duplicate registrations, historical approvals and timestamped events. Verify interrupted event and account cleanup can be retried.
- [ ] Test approved image upload, replacement and removal, with app roles and cloud IAM. Confirm whether any old profile tokens remain usable and review how draft media should be stored.
- [ ] Test the inquiry form with valid and missing App Check tokens, with the bound secret, across distinct clients. Check rate-limit response, TTL configuration and logs without recording private content.
- [ ] Invoke `refreshPublicStats` with the staging admin and verify the scheduled function independently. Check published and draft blog reads, deep-link rewrites, approved media, mobile keyboard and screen-reader behavior, and the browsers the club supports.

## Remaining operational work

Real OAuth and App Check tokens, deployed IAM and indexes, scheduled refresh delivery, official domains and links, and live data counts require staging or production-owner verification. Public event and blog archive search and some admin lists still filter downloaded records to preserve full text matching over the existing data. Homepage event discovery and approval queue reads are bounded. Plan a dedicated search index if archive size warrants it. Site-wide social metadata is included. Per-article crawler previews require serving route-specific metadata after the canonical domain is confirmed.
